# customer-voice · 소셜 리스닝 (고객의 목소리)

사람들이 이 문제를 **어떤 상황에서, 어떤 말로** 고민하는지 찾는다. 이미 서비스를 쓰는 사람뿐 아니라 **아직 아무것도 쓰지 않는 사람**의 목소리를 함께 본다.

결과는 사실이 아니라 **가설**이다. 글을 많이 쓰는 사람과 불편이 큰 사람이 더 잘 보이기 때문이다. 가설을 확인하는 일은 이후 고객 인터뷰에서 한다.

## 공통 규칙

- **참고 자료**: 작업 공간(대화 첨부, 프로젝트 파일, 지시문)에 맥락 파일이나 리서치 가이드가 있으면 먼저 읽는다. 그 안의 데이터 소스, 민감한 정보에 대한 주의점, 체크리스트를 이 스킬의 기준보다 우선한다.
- **원문 확인**: 검색 결과 요약은 잘려 있어 실제 말을 알 수 없다. 반드시 글을 **열어 읽고** 정리한다. 열어 보지 못한 내용은 쓰지 않는다.
- **원문 인용 금지**: 게시글과 리뷰를 그대로 옮기지 않는다. 닉네임, 나이·지역·직장 같은 식별 단서를 지운 **요약**으로만 쓴다. "사람들의 말"도 요약한 짧은 말로 쓴다.
- **수집 금지**: 대량 수집(크롤링)을 하지 않는다. 웹 검색으로 공개된 페이지를 열람만 한다. 로그인이 필요한 곳은 보지 않는다.
- **비율로 바꾸지 않기**: "글 10개 중 7개"를 "사용자의 70%"로 쓰지 않는다. 빈도는 "자주 보임 / 가끔 보임 / 한두 번"으로만 쓴다.
- **출처**: 요약마다 [사이트 종류, 확인일, 링크]를 붙인다. 링크를 열지 못했으면 "확인 필요".
- **결과는 파일로**: 다운로드할 수 있는 파일. 기본 `.md`, 사용자가 원하면 Word나 PDF. 파일명은 `customer-voice.md`, 사용자가 정한 파일명 규칙이 있으면 그것을 따른다.
- **메모리**: 본문은 저장하지 않는다. `[소셜 리스닝 완료] 가장 자주 보인 불편 1줄`만 남긴다.
- **분량**: A4 2~3쪽 안쪽.

## 먼저 읽을 것

작업 공간의 조사 파일을 모두 읽는다.

| 파일 | 가져올 것 |
|---|---|
| `market-landscape.md` | 시장 정의 → 검색어의 중심, PEST의 S 항목 → 확인할 가설 |
| `competitive-intel.md` | 경쟁사 이름 → 비교·리뷰 검색어, 경쟁사의 이용자 반응 요약 → 더 깊이 볼 곳 |

## 1. 입력 확인

- 리서치 주제 정의와 시장 정의: 지시문이나 메모리에 있으면 확인만 한다. 없으면 묻는다. 아예 없으면 `/research-topic`을 먼저 하자고 안내한다.
- 누구의 목소리를 볼지: 기본은 이용자. 주제에 따라 결정자, 지불자, 돌보는 사람, 전문가 등 함께 볼 역할을 묻는다.
- 사용자가 이미 아는 커뮤니티나 앱이 있으면 받는다.
- 조사 깊이: 가볍게 / 보통 / 깊게 (기본: 보통)

## 조사 깊이

| 깊이 | 단계당 웹 검색 | 열어 읽을 글 | 사용 장면·불편 | 가설 |
|---|---|---|---|---|
| 가볍게 | 1~2회 | 3~5건 | 3~5개 | 2~3개 |
| 보통 | 3~4회 | 6~10건 | 5~8개 | 3~5개 |
| 깊게 | 5~6회 | 10~15건 | 8~12개 | 5개 |

## 2. 검색어 만들기

사람들이 실제로 쓰는 **생활 언어**로 검색어를 만든다. 전문 용어 대신 사람들이 고민을 말할 때 쓰는 말로 검색한다. 네 갈래로 만든다.

| 갈래 | 검색어 예 |
|---|---|
| 불편 | "[문제] 너무 귀찮", "[문제] 어떻게 해요", "[서비스 종류] 단점", "[서비스 종류] 후기 별로" |
| 바람 | "[문제] 이런 거 없나", "[서비스 종류] 추천", "[문제] 있었으면" |
| 비교 | "[경쟁사 A] vs [경쟁사 B]", "[경쟁사] 대신", "[경쟁사]에서 갈아탐" |
| 결정 | "[서비스 종류] 결국 샀", "[서비스 종류] 가입한 이유", "[서비스 종류] 돈값" |

## 3. 어디서 찾나

| 소스 | 무엇이 보이나 | 주의 |
|---|---|---|
| 공개 커뮤니티·Q&A | 아직 서비스를 쓰지 않는 사람의 고민, 쓰는 말 | 로그인이 필요한 카페·단톡방은 보지 않는다 |
| 앱 리뷰, 쇼핑몰 리뷰 | 이미 쓰는 사람의 불만과 칭찬, 그만둔 이유 | 별점 1·5점에 극단적인 글이 몰린다 |
| 검색 트렌드 | 관심이 언제, 어떤 말로 늘거나 줄었나 | 검색량은 관심이지 수요나 구매가 아니다 |
| 영상 댓글, 블로그 후기 | 실제로 써 본 과정, 대신 쓰는 방법 | 광고·협찬 글을 걸러낸다 |

## 4. 무엇을 정리하나

| 항목 | 볼 것 |
|---|---|
| 사용 장면 | 언제, 어디서, 무엇을 하다가 이 문제를 떠올리나 |
| 불편 | 무엇이 어렵고 귀찮고 불안한가. 역할별로 나누고, 종류(기능: 안 되는 것 / 감정: 걱정·답답함 / 관계: 남의 눈·주변 반응)와 심각도(높음·보통·낮음)를 단다 |
| 바람 | "이런 게 있으면" 하는 것, 이상적인 결과 |
| 지금 대신 하는 것 | 다른 서비스, 제품, 지인에게 묻기, 그냥 참기 |
| 비교와 갈아타기 | 무엇과 무엇을 견주나, 고를 때 쓰는 기준, 갈아탄 이유 |
| 그만두는 이유 | 써 보다가 그만둔 이유 (리뷰에서 특히 잘 보인다) |
| 결정의 계기 | 사거나 가입하게 만든 것: 남의 후기, 급함, 값어치를 느낌, 위험이 사라짐(무료 체험·환불), 전문가 추천, 한정 |
| 사람들의 말 | 이 문제를 부를 때 쓰는 표현 (요약한 짧은 말로). 업계가 쓰는 말과 다르면 함께 적는다 |
| 돈 신호 | 이미 돈을 쓰고 있는 것, "이 정도면 낸다 / 안 낸다"는 반응 |
| 정보를 얻는 곳 | 이 문제를 어디서 먼저 찾아보나 (검색 포털, 영상, 커뮤니티, AI 챗봇, 지인). 자주 보인 커뮤니티 이름 |

## 5. 가설과 인터뷰 질문

- **가설**: 위 정리에서 "[누가] [어떤 상황에서] [무엇 때문에] [어떤 불편]을 겪는다" 형식으로 만든다. 가설마다 근거 요약 번호와 빈도(자주 / 가끔 / 한두 번)를 단다.
- **인터뷰 질문**: 가설을 확인할 질문을 3~5개 만든다. 의견("이런 서비스 쓰겠어요?")이 아니라 **최근의 실제 행동**을 묻는다. 예: "마지막으로 점심 메뉴 때문에 고민했을 때 어떻게 했어요?"

## 6. 이 자료의 한계

어떤 사람의 목소리가 빠졌는지 적는다. 글을 안 쓰는 사람, 특정 연령대, 로그인이 필요한 곳, 특정 플랫폼에 몰린 반응 등.

## 마무리

파일을 만든 뒤 세 줄로 알린다.

## 품질 체크리스트

- [ ] 모든 요약을 글을 열어 확인했고, 출처 링크와 확인일이 있다
- [ ] 원문을 그대로 옮기지 않았고, 식별 단서가 없다
- [ ] 빈도를 %로 바꾸지 않았다
- [ ] 이미 쓰는 사람과 아직 안 쓰는 사람의 목소리를 모두 봤다
- [ ] 불편마다 종류와 심각도가 있다
- [ ] 가설마다 근거 번호가 있다
- [ ] 인터뷰 질문이 지난 행동을 묻는다
- [ ] 이 자료의 한계를 적었다
- [ ] 참고 자료가 있었다면 그 기준을 지켰다

## 예시 (줄임)

> 사용 장면: 오전 회의가 끝나고 점심시간 10분 전, 동료와 메뉴를 정할 때
> 불편: 매일 메뉴를 고르는 게 일처럼 느껴짐 (감정, 높음, 자주 보임)
> 그만두는 이유: 정기 배송이 재택 날에도 와서 버리게 됨 (가끔 보임)
> 결정의 계기: 첫 주 무료 체험 (위험이 사라짐)
> 사람들의 말: "알아서 오는 점심" / 업계의 말: "정기 구독"
> 가설: 출근일이 일정하지 않은 직장인은 고정 배송 때문에 구독을 그만둔다

## 하지 않는 것

- 원문 복사, 대량 수집, 로그인이 필요한 곳 열람
- 게시글 수를 사용자 비율이나 시장 규모로 바꾸기 → `market-scanner`
- 경쟁 서비스 비교 → `competitor-analysis`
- 타겟 결정 → `stp`
