# expert-review · 전문가 검토

캔버스가 **정말 괜찮은지, 괜찮아 보이기만 하는지** 확인한다. 한 가지 눈으로 보면 사각지대가 생긴다. 서로 다른 전문가 3명의 **관점**을 정하고, 관점마다 **평가 질문을 먼저 뽑은 뒤 그 질문에 답하는 방식**으로 검토한다. 그다음 어디서 의견이 모이고 어디서 갈리는지 정리한다.

- 모두 동의한 것 → 강한 신호. 그대로 받아들인다.
- 의견이 갈린 것 → 결정할 지점. 사용자가 고른다.
- 아무도 다루지 않은 것 → 사각지대. 더 본다.

사실이 맞는지는 `fact-check`가 본다. 이 스킬은 **전략과 사업 모델이 설득력 있는지**를 본다.

## 공통 규칙

- **고르는 건 사용자**: 전문가와 검토 방식은 AI가 제안하고 사용자가 고른다. 아래 **[멈춤]** 표시가 있는 곳에서는 제안을 보여 주고 **멈춰서 사용자의 답을 기다린다. 답을 받기 전에는 검토를 시작하지 않는다.** 한 번에 한 가지만 묻는다.
- **알아서 해 달라고 하면**: 사용자가 "알아서 해 줘", "추천대로 해 줘"라고 하면 남은 멈춤을 건너뛰고 추천대로 진행한다. 결과 파일 맨 위 "정한 방식"에 "AI 추천으로 정함 (사용자 확인 없음)"이라고 적는다.
- **질문이 먼저**: 검토는 정한 평가 질문에 하나씩 답하는 방식으로만 한다. 질문 밖의 일반론("마케팅을 강화하세요")은 쓰지 않는다.
- **관점은 섞지 않는다**: 한 전문가의 관점으로 쓸 때는 그 역할이 실제로 신경 쓰는 것만 본다. 앞 전문가의 결론을 끌어오거나 맞추지 않는다. 의견이 다르면 다른 대로 둔다. 합치는 일은 마지막 종합에서만 한다.
- **참고 자료**: 작업 공간(대화 첨부, 프로젝트 파일, 지시문)에 맥락 파일이나 리서치 가이드가 있으면 먼저 읽고 브리핑에 넣는다. 그 안에 정해 둔 전문가 역할이나 검토 기준이 있으면 그것을 따른다.
- **검토 결과 존중**: 팩트체크(`fact-check.md`)에서 틀렸다고 판정된 내용은 브리핑에 넣지 않는다. 부분 일치나 확인 불가는 "확인 필요"를 단다.
- **결과는 파일로**: 대화창 답변이 아니라 **다운로드할 수 있는 파일 두 개**를 처음부터 함께 만든다. 원본 `expert-review.md`와 보기용 `expert-review.html`(아래 "보기용 HTML"). 사용자가 원하면 Word나 PDF도 준다. 사용자가 정한 파일명 규칙이 있으면 그것을 따른다.
- **메모리**: 본문은 저장하지 않는다. `[전문가 검토 완료] 전체 확신도 · 가장 시급한 보완 1줄`만 남긴다.
- **읽히는 문장으로 쓰기**: 결과(md와 html 모두)는 이 조사를 처음 보는 사람이 읽고 바로 이해할 수 있게 쓴다.
  - 항목마다 **무엇이 일어나고 있는지 → 근거 → 그래서 우리 주제에 무슨 뜻인지**를 완전한 문장("~다")으로 쓴다.
  - 단어, 화살표(→), 가운뎃점(·)만 이어 붙인 메모체로 쓰지 않는다. 화살표는 순서나 흐름을 보여 줄 때만 쓴다.
  - "한 줄"로 쓰라는 곳도 완전한 한 문장으로 쓴다. 표 칸에 다 못 쓰면 표 아래에 번호를 달아 문장으로 풀어 쓴다.
  - 줄임말과 전문 용어(TAM, SAM, SOM, CAGR, PEST 등)는 처음 나올 때 한 번 풀어 쓴다.
  - 예: (X) "외식 물가 상승 → 기회 · 곧" / (O) "외식 물가가 최근 3년 동안 약 11% 올랐다[통계청, 2025]. 점심값 부담이 커질수록 가격이 정해진 구독이 매력적으로 보일 수 있어, 우리 주제에는 1~3년 안에 기회가 된다."

## 1. 입력 확인

작업 공간에서 아래를 찾는다. `-v2`가 있으면 그것을 우선한다.

| 파일 | 없을 때 |
|---|---|
| 비즈니스 캔버스 (`business-canvas.md`) | STP만 있으면 STP를 검토 대상으로 할지 묻는다. 둘 다 없으면 멈추고 `/stp`나 `/business-canvas`를 먼저 하라고 안내한다 |
| STP (`stp.md`) | 있는 것만 읽는다 |
| 조사 파일 (시장 스캔, 경쟁사, 소셜 리스닝) | 있는 것만 읽고, 없는 조사는 브리핑에 "안 함"으로 적는다 |
| 팩트체크 (`fact-check.md`) | 없어도 진행. 브리핑에 "팩트체크 안 함"을 적는다 |

읽은 파일 목록을 보여 주고 모드를 확인한다.

## 2. 전문가 정하기

세 명 모두 사용자가 고른다. 캔버스와 STP를 읽고 **이 캔버스에 가장 날카로운 의견을 줄 역할** 후보를 5~6개 제안한다. 사용자가 미리 정해 둔 역할이 있으면 후보에 넣는다.

| 캔버스가 이렇다면 | 후보 역할 예 |
|---|---|
| 사업 전체가 말이 되는지, 칸끼리 맞물리는지 봐야 한다 | 전략 컨설턴트 (이 분야 스타트업 자문: 타겟 근거, 포지셔닝, 누가 돈을 내나, 무너지는 가정) |
| 돈을 내는 사람이 이용자와 다르다 | 지불자 쪽 담당자 (기업 복지 담당, 기관 구매 담당, 보험·제휴사 상품 기획자) |
| 이용자가 정말 쓸지가 가장 불안하다 | 실제 이용자 대표 |
| 규제·인허가·개인정보가 걸린다 | 인허가·규제 담당자 |
| 현장 전문가의 추천이나 업무 흐름이 중요하다 | 해당 분야 현장 전문가 |
| 포지셔닝·메시지가 약하다 | 브랜드 전략가 |
| 채널이 약하거나 고객을 모으는 비용이 클 것 같다 | 고객 획득 전문가 |
| 성장 경로가 불분명하다 | 성장 전략가 |

- 후보마다 **왜 이 캔버스에 필요한지** 한 줄을 단다(어느 칸, 어느 가정이 약해서인지).
- 후보끼리 관점이 겹치지 않게 한다. 사업 전체를 보는 역할 하나, 반대편(지불자·이용자·규제·현장) 역할 하나 이상이 섞이게 추천한다.
- 참고 자료에 그 분야의 전문가 역할 예가 있으면 그것을 먼저 쓴다.

**[멈춤 1]** 후보를 보여 주고 3명 조합을 하나 추천한 뒤 "어느 세 명으로 할까요?"를 묻는다. 사용자가 다른 역할을 말하면 그대로 쓴다. 고른 세 명의 관점이 많이 겹치면 한 번만 알려 준다.

## 3. 검토 방식 정하기

고른 세 전문가마다 아래를 제안한다.

- **역할 설명** 2~3줄: 누구의 눈으로 보는지, 무엇을 가장 중요하게 여기는지
- **평가 질문 5개**: 그 역할이 반드시 물을 질문. 마지막 질문은 늘 "이 캔버스가 놓친 것은 무엇인가"
- **특히 볼 칸과 가정**: 캔버스의 칸 이름과 가정 목록 번호

모든 전문가의 답 형식은 같다.

1. **강점** 2개: 문서의 어느 부분인지
2. **우려** 2~3개: 왜 문제인지, 근거 위치
3. **빠진 것** 1~2개
4. **가장 중요한 권고** 1개: 한 문장, 바로 할 수 있는 것
5. **확신도**: 상·중·하와 이유 한 줄

규칙: 질문마다 2~4문장으로 답한다(무엇이 문제인지, 근거, 그래서 무엇을 해야 하는지). 칭찬은 짧게, 모르는 것은 모른다고, 법령 해석은 확정하지 않는다, 근거는 브리핑 안에서만 찾는다.

**[멈춤 2]** 세 전문가의 역할 설명과 평가 질문을 보여 주고 "이대로 부를까요? 고칠 질문이 있나요?"를 묻는다.

## 4. 브리핑 만들고 관점별로 검토하기

### 브리핑 묶음

세 관점이 **똑같이** 볼 근거를 2000자 안쪽 브리핑으로 먼저 정리한다. 검토는 이 브리핑 안에서만 근거를 찾는다.

```
## 브리핑
### 주제와 시장
### 타겟과 포지셔닝 (STP)
### 캔버스 9칸 (칸마다 한두 줄, "가정" 표시 유지)
### 가정 목록 (번호 유지)
### 조사 핵심 (시장 규모, 경쟁 빈틈, 고객 불편 각 2~3줄)
### 안 한 조사, 팩트체크에서 확인 필요로 남은 것
### 검토 초점 (전체 / 집중 질문)
```

### 관점별 검토

- 전문가 한 명씩 차례로, 그 사람의 평가 질문 5개에 **질문마다 답한다**(질문 번호, 답, 근거 위치). 그다음 답을 바탕으로 정한 답 형식(강점 / 우려 / 빠진 것 / 권고 / 확신도)으로 정리한다.
- 한 전문가를 다 쓴 뒤 다음 전문가로 넘어간다. 앞 전문가의 결론을 근거로 쓰지 않는다.
- 근거가 브리핑에 없으면 "브리핑에 근거 없음"이라고 쓰고 추측하지 않는다.

## 5. 종합

세 관점의 검토를 모아 종합한다. 모든 항목에 누구의 의견인지 `[역할 이름]`처럼 표시한다.

1. **모두 동의한 것 ⭐**: 세 명이 같은 강점·우려·권고를 짚은 것. 가장 믿을 만한 신호
2. **두 명이 동의한 것**
3. **의견이 갈린 것**: 누가 무엇을 어떻게 다르게 봤는지 양쪽 다 + **사용자가 결정할 것**
4. **아무도 다루지 않은 것**: 브리핑에서 비어 보이는데 아무도 짚지 않은 것. "진행자 의견"이라고 표시
5. **확신도**: 전문가별 상·중·하와 이유, 그리고 전체 판정
   - 셋 다 상, 또는 상 2 + 중 1 → **상**
   - 섞여 있음, 또는 하가 1개 → **중** (하를 준 이유를 먼저 짚는다)
   - 하가 2개 이상 → **하** (캔버스를 다시 볼 것)
6. **보완할 것 3~5개**: 무엇을, 누구의 의견에서(합의 / 이견 / 한 명), 캔버스의 어느 칸·어느 가정과 이어지는지, 확인 방법(인터뷰, 원문 확인, 시험 판매 등), 우선순위(상·중·하)

동의와 이견이 하나도 없다고 억지로 만들지 않는다. 없으면 "뚜렷한 이견 없음"이라고 쓴다.

## 보기용 HTML

md와 같은 내용을 **도식으로 바꿔** 한눈에 보이게 한 `expert-review.html`을 처음부터 함께 만든다. md의 표를 HTML 표로 옮기는 것이 아니다.

- **md가 원본**: 보완 단계에는 md를 쓴다. HTML에만 있는 내용을 넣지 않고, md를 고치면 HTML도 고친다. 다시 검토하면 둘 다 `-v2`로 만든다.
- **표는 맨 아래에만**: 위쪽 도식 부분에는 `<table>`을 쓰지 않는다. 도식은 CSS 격자(grid·flex)와 인라인 SVG로 그린다. 표는 맨 아래 "자세히 보기"(`<details>`로 접어 둠)에만 둔다.
- **파일 하나로 완결**: CSS는 `<style>` 안에 넣는다. 외부 스크립트·웹 폰트·이미지 링크를 쓰지 않는다. 흰 배경, 본문 최대 너비 960px, 휴대폰에서는 여러 열 도식을 1열로 접는다. A4로 인쇄해도 잘리지 않게 한다.
- **전문가 색은 고정**: 전문가 1 남색 `#2f4b7c`, 전문가 2 초록 `#2e7d4f`, 전문가 3 주황 `#c8702a`. 모든 도식에서 같은 사람은 같은 색이다.
- **참고 자료**에 시각화 기준이 있으면 그것을 따른다.

**이 화면의 질문**: 전문가들은 어디서 동의하고 어디서 갈렸고, 무엇부터 고쳐야 하나?

**도식** (위에서 아래 순서)

1. **한눈에 보기**: 전체 확신도를 큰 원형 배지(상 초록 / 중 주황 / 하 빨강)로, 옆에 카드 3장(가장 강한 신호 / 결정할 것 / 가장 먼저 보완할 것).
2. **전문가 카드 3장** (md "전문가"): 가로 3열. 카드 위에 전문가 색 띠와 역할 이름, 보는 것 한 줄, 확신도 막대 3칸(상·중·하 중 해당 칸까지 채움), 가장 중요한 권고 한 문장.
3. **합의 벤 다이어그램** (md "모두 동의한 것", "두 명이 동의한 것"): 인라인 SVG 원 3개를 삼각형으로 겹친다. 원 색은 전문가 색. 세 원이 모두 겹친 가운데에 ⭐ 합의 항목, 두 원만 겹친 곳에 두 명 합의 항목, 원의 겹치지 않는 부분에 그 전문가만 짚은 우려를 짧게 적는다. 항목이 길면 번호만 넣고 원 아래에 번호별 한 줄 목록.
4. **이견 저울** (md "의견이 갈린 것"): 이견마다 가로 줄 하나. 왼쪽 말풍선에 한 전문가 의견(그 전문가 색), 오른쪽 말풍선에 다른 전문가 의견, 가운데 아래에 "결정할 것" 노란 상자.
5. **사각지대** (md "아무도 다루지 않은 것"): 회색 점선 상자, "진행자 의견" 배지.
6. **보완할 것 → 캔버스 연결** (md "보완할 것"): 작은 9칸 캔버스 판(표준 배치)을 그리고, 보완할 것이 걸린 칸에 번호 표시(①②③)를 붙인다. 판 옆에 번호별 카드: 무엇을, 누구의 의견(전문가 색 점), 확인 방법, 우선순위 배지.

**자세히 보기 (표)**: 관점별 검토(질문별 답), 의견이 갈린 것 표, 보완할 것 표, 브리핑과 평가 질문.

**가장 강조할 것**: 결정할 것과 가장 먼저 보완할 것.

**조심할 것**
- 관점별 검토를 도식에 옮기면서 뜻을 바꾸지 않는다. 줄일 때는 원래 답의 단어를 쓴다.
- 진행자 의견은 전문가 색을 쓰지 않는다. 회색으로만.

## 마무리

파일을 만든 뒤 알린다.

1. 파일 이름 두 개: `expert-review.md`(원본, 보완할 때 첨부하는 파일)와 `expert-review.html`(보기용)
2. 전체 확신도와 결정할 것 1개
3. "결정할 것을 정한 뒤 `/business-canvas 전문가 검토 반영해서 보완해 줘` + `expert-review.md` 로 보완본을 만드세요."

## 품질 체크리스트

- [ ] 메모체(단어·화살표만 이은 줄) 없이 완전한 문장으로 썼고, 항목마다 "그래서 무슨 뜻인지"가 있다
- [ ] md와 html을 둘 다 만들었고, 두 파일의 내용이 같다
- [ ] html 위쪽에 표가 없고, "보기용 HTML"에 정한 도식이 모두 그려졌다
- [ ] 멈춤 2곳에서 사용자의 답을 받았다. 받지 않았다면 "AI 추천으로 정함"을 적었다
- [ ] 세 전문가를 사용자가 골랐고(또는 "AI 추천으로 정함"), 관점이 겹치지 않고 캔버스의 약한 곳과 이어진다
- [ ] 세 관점이 같은 브리핑을 근거로 썼다
- [ ] 관점마다 평가 질문 5개에 하나씩 답했고, 질문별 답이 파일에 있다
- [ ] 앞 전문가의 결론을 끌어와 맞추지 않았다
- [ ] 팩트체크에서 틀렸다고 판정된 내용이 브리핑에 없다
- [ ] 의견이 갈린 것마다 "결정할 것"이 있다
- [ ] 보완할 것마다 캔버스 칸이나 가정 번호가 있다
- [ ] 참고 자료가 있었다면 그 기준을 지켰다

## 예시 (일부)

> **고른 전문가**: 칸끼리 맞물리는지 보려고 전략 컨설턴트를, "회사가 복지비로 낸다"는 가정 3이 가장 약해서 기업 복지 담당자를, 채널 칸이 "SNS 광고"뿐이라서 고객 획득 전문가를 골랐다.
>
> **⭐ 모두 동의한 것**: 세 전문가 모두 "출근일에만 받는 구독"이 경쟁사와 분명히 다르다고 봤다.
>
> **의견이 갈린 것**: [전략 컨설턴트]는 매출이 큰 기업 계약에 집중하라고 했고, [고객 획득 전문가]는 개인 구독으로 수요부터 증명하라고 했다. 첫 3개월에 누구에게 먼저 팔지는 사용자가 정해야 한다.
>
> **확신도**: [기업 복지 담당자]가 "회사에 이런 비용을 쓸 예산 항목이 없다"며 하를 줘서, 전체 확신도는 중이다.
>
> **가장 먼저 보완할 것**: 복지 담당자 3명을 인터뷰해 예산 항목이 있는지 확인한다. 수익원 칸과 가정 3에 걸린 문제다.

## 하지 않는 것

- 사실이 맞는지 확인하기 → `fact-check`
- 캔버스를 직접 고치기 → `business-canvas` 보완 모드
- 새로 조사하기 → `market-scanner`, `competitor-analysis`, `customer-voice`
- 최종 결정 대신 내리기 (전문가 의견은 판단 재료다. 결정은 사용자가 한다)
